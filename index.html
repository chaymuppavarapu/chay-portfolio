Shipped MVP

Fync

A shared-wallet fintech platform with automatic contribution tracking and settlement—because groups deserve to know who funded what and who owes whom.
React Native Expo Supabase PostgreSQL Razorpay
17 Screens
7+ DB Tables
25 SQL Migrations
18K Lines of Code

The Problem: When groups share expenses, someone always loses track of who paid what. Existing split-bill apps settle after the fact. I wanted money to be shared by design—with automatic contribution tracking, proportional spending, and fair settlement.

What I Built: A 17-screen React Native app with Supabase backend, phone OTP auth, Razorpay top-ups, and a sophisticated PostgreSQL layer handling money tags, proportional splits, dues, and balance reconciliation across shared and personal wallets.

Hardest Technical Challenge: Competing database triggers caused double-balance deductions during shared-wallet transactions. I spent days debugging with logs, reproducing on test wallets, and implementing idempotent processing guards (processed_at checks, skip-if-already-set logic) to ensure financial correctness.

React Native (Expo) | supabaseClient.js Supabase Auth | Phone OTP PostgreSQL | RLS Policies | Triggers | transactions | balances | money_tags | dues Razorpay WebView | Add Funds | DB Credit
Key Lesson: Financial correctness is a backend problem. RLS + triggers + race conditions matter more than UI polish. I learned to debug distributed state where one transactions row is touched by approval, balance, and tagging logic simultaneously.

Churn Prediction + RAG

An ML API that predicts customer churn from behavioral features and explains risk in plain language using retrieval-augmented patterns—with graceful fallbacks when external services fail.
Python FastAPI XGBoost SHAP FAISS OpenAI API Streamlit
5 API Endpoints
93% ROC AUC
6 RAG Patterns
700 Lines of Code

The Problem: Most churn prediction systems are black boxes. Stakeholders get a probability score with no actionable context. I wanted to build a system that not only predicts churn but explains why—using known patterns and LLM-augmented reasoning.

What I Built: A FastAPI service with 5 endpoints serving real-time churn risk scores. The RAG layer uses sentence embeddings + FAISS similarity search to retrieve contextual explanations, with OpenAI as an optional polish layer. I built a Streamlit dashboard for non-technical users to interact with the system, upload data, and trigger retraining.

Hardest Technical Challenge: Making the system fault-tolerant. SHAP TreeExplainer fails across XGBoost versions, so I implemented a proxy fallback using scaled_value times global_importance. When OpenAI API is unavailable, the system falls back to deterministic template text. Every external dependency has a graceful degradation path.

FastAPI | /predict | /explain | /insights | /retrain | XGBoost | predict_proba + SHAP (or proxy fallback) | RAG: SentenceTransformer | FAISS | OpenAI (optional) | Streamlit | Dashboard + CSV Upload + Retrain
Key Lesson: Production ML is not about the model—it is about the system around it. Fallbacks, idempotency, and clear contracts between components matter more than a 1% accuracy improvement. I learned to design for failure, not just for success.
Working System

AI Career Copilot

A multi-agent system that turns a career goal, job description, and resume into a structured prep plan—with quality gates, retry loops, and persistent memory of only high-quality outputs.
Python Groq API Llama 3.1 Streamlit PyPDF2
3 Agents
550 Lines of Code
2 Interfaces
7 Quality Threshold

The Problem: Generic ChatGPT answers do not prepare you for specific roles. I wanted a system that reads a job description, analyzes your resume against it, and generates a personalized, step-by-step prep plan—with quality checks at every step.

What I Built: A multi-agent orchestration system with three specialized roles: a Planner that breaks goals into prioritized tasks, an Executor that generates personalized guidance using profile + resume + past high-quality outputs, and a Critic that scores outputs 1 to 10 and triggers retries for sub-threshold results. Only outputs scoring 7 or above are persisted to memory for future tasks.

Hardest Technical Challenge: Getting three agents to return valid JSON every time. I tried free-form text first, then added strict schema prompts, parsers, and retry loops in each agent. It took days of tuning before the planner/executor/critic pipeline was stable enough to run end-to-end without manual intervention.

Goal + JD + Resume | Planner | JSON task list (id, task, priority) | Executor + memory.json | JSON result | Critic | score >= 7? | store in memory : retry (max 2)
Key Lesson: Designing contracts between agents (JSON schemas) matters more than prompt cleverness. Orchestration—who calls whom, when to retry, what to store—is a separate skill from "calling an LLM." I learned that critics as code policy (approved = score >= 7) beat trusting the model's boolean.
Research Project

YouTube Trend Analysis

A data analytics pipeline that transforms raw YouTube API data into actionable insights about virality, engagement patterns, and regional content trends.
Python YouTube Data API Pandas Matplotlib Seaborn Jupyter
1,000+ Videos Analyzed
15+ Visualizations
10+ Features
3-5 Countries

The Problem: YouTube generates massive amounts of public data, but creators guess at what makes content viral. I wanted to build a data-driven approach to understanding engagement patterns, best upload times, and regional content trends.

What I Built: A complete analytics pipeline: API data collection with pagination and quota handling, preprocessing pipeline for nested JSON normalization, feature engineering for engagement rates, and 15+ visualizations comparing categories, regions, and temporal patterns.

Hardest Technical Challenge: Handling raw API data efficiently. Nested JSON structures, missing fields across videos, and API quota limitations required building a robust preprocessing pipeline with reusable cleaning functions and local caching to avoid re-fetching.

Key Lesson: Real-world data is messy. Tutorials provide clean datasets; production APIs require deep debugging, quota handling, and scalable preprocessing. This project taught me to think analytically rather than just codically.
What I Have Learned

Lessons From Building

These are not theoretical principles. They are things I learned while debugging triggers at 2 AM, tuning agent prompts, and shipping MVPs.

01. Financial correctness is a backend problem

RLS policies, database triggers, and race conditions matter more than UI polish. I learned this debugging double-balance deductions in Fync's PostgreSQL layer.

02. Design for failure, not just success

Every external dependency needs a fallback. SHAP proxy when TreeExplainer fails. Deterministic RAG when OpenAI is unavailable. The system must work when components break.

03. Agent contracts matter more than prompts

Getting three LLM agents to return valid JSON consistently required schema design, parser retries, and orchestration logic—not just better prompts.

04. Real-world data is messy

Tutorials provide clean datasets. Production APIs have nested JSON, missing fields, and quota limits. Building robust preprocessing pipelines is a skill in itself.

05. Curiosity compounds

Every project taught me something that made the next one better. Fync's backend knowledge informed the ML API's fault tolerance. The ML API's RAG patterns informed the multi-agent system.

06. I still have a lot to learn

The biggest lesson is how much I do not know yet. That is why I am looking for a team that will push me to become a better engineer and builder.
